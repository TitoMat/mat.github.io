About

Case study

A document intelligence platform, end to end

One system, taken from intake to searchable record. This is the deepest automation I have designed and owned, so I can talk through every decision below in detail. The business domain, organisation, data, and infrastructure specifics are deliberately left out — what remains is the engineering.

01

Ingestion, extraction & AI analysis pipeline

Turning untrusted uploaded documents into verified, structured, searchable records — with no human babysitting each file, and with inference kept inside the network.

Context

The platform needed to accept documents from several entry points — interactive uploads, trusted machine ingestion, and attachments hanging off tasks and activities — and turn all of them into the same thing: a verified, structured, searchable record. Doing that by hand does not scale, and bolting a model onto the front of it without a safety layer produces confident nonsense.

Three constraints shaped everything: the input is untrusted, the authoritative bytes live on a shared filesystem rather than inside the application, and policy required that inference never leaves the network — so no cloud AI services.

Intake, storage safety & integrity

  • Every intake path writes to a canonical location and registers a manifest row — relative path, size, SHA-256, storage class, lifecycle state, retention class. The database is the source of truth for where and what a file is; the blob store only holds bytes.
  • Path safety fails closed in three independent layers: absolute paths, .. segments, NULs and backslashes are rejected; every path segment is walked with lstat and symlinks refused; the resolved real path must stay inside the configured root. Namespace allowlists stop a bad configuration from reaching outside approved subtrees.
  • Source size and a streamed SHA-256 are verified against authoritative metadata before any processing starts, and the hash of extracted text is re-verified before results are persisted. A corrupt or swapped file cannot be silently analysed.
  • Derived artifacts are published atomically: existence check, exclusive create, fsync, then rename — with the temporary file unlinked on failure and attempt-scoped keys so two attempts can never collide.

Extraction

Extraction is a decision, not a default. The engine reads page metadata, probes each page for native text, and then routes: all-native PDFs take direct extraction; scanned or mixed PDFs go through OCR and additionally produce a searchable PDF artifact; images go straight to recognition. Office files take a different road entirely.

  • Office parsing runs in a separate sandboxed subprocess with a hard heap cap, and is guarded against zip bombs: maximum archive entries, per-entry and total uncompressed ceilings, worksheet, row, cell and shared-string limits, and a global output cap with an explicit truncation marker rather than silent loss.
  • External tools are spawned with shell: false, escalating timeouts that fall through to SIGKILL, and output caps — each failure mapped to a controlled error code rather than a stack trace.
  • Startup fails closed if a tool version or a required OCR language pack is missing, instead of degrading to worse output later.
  • The output contract is fixed: normalized text, meaningful-text thresholds, and metadata carrying schema version, method, page counts, warnings, engine versions and a text SHA-256.

AI analysis

  • Inference is self-hosted, so document content never leaves the network. That single choice drove most of the operational design below.
  • Structured output is enforced by handing the model a JSON Schema and taking the response at temperature 0 with reasoning disabled. That was not arbitrary: a reasoning model was returning empty responses under those constraints, so the design records the reason in code rather than leaving it as folklore.
  • Document text is treated as data, not instructions — wrapped and explicitly instructed against obeying anything embedded inside it, which is the practical defence against prompt injection through uploaded files.
  • Long documents use chunked map-reduce with page tracking, so a long file is analysed in pieces and page references survive the merge.
  • Two more defensive layers sit behind the model: a strict validator, and sanitizers that clamp hostile or absurd values before they reach a record.
  • Partial failure is honest. A chunk that exhausts its retries is skipped and surfaced as a warning carried into the final result; the run only fails outright if no chunk succeeded. Over-budget input is reported as truncated rather than quietly dropped.
  • Every result records model identity, prompt version, analysis method, chunk count and inference duration — so an output produced last month can be explained today.

Orchestration & reliability

The part that makes the rest trustworthy. Work is a durable row in a state machine with an append-only event log; the queue carries wake-ups, not truth.

  • Claim selection uses row locks with skip_locked, so several workers can compete without blocking each other. Every transition — claim, start, complete, fail — re-validates a claim token, and the attempt counter increments at start.
  • Leases expire. A worker that dies mid-job is recovered by a sweep that requeues or fails the job based on how many attempts remain, so nothing is stranded in a processing state forever.
  • Retry ownership is deliberately split, and the reasoning is documented in the code: jobs with no database state machine get queue-owned exponential retries, while jobs that do have one get a single-attempt wake-up and let the database own the retries. That prevents a queue retry and a reconciler sweep from double-processing the same work.
  • Deterministic job ids act as the dedup key — a re-enqueued job collapses into the existing one — with a create-or-get fallback at the database level as a second line of defence.
  • Priority classes separate interactive work from system-chained and backfill sweeps, because the consumer processes one job at a time and priority is the only thing deciding what runs next.
  • Unsupported media is reported once and deliberately never retried; failed jobs are retained with their typed error code, and requeue is admin-gated with an attempt-exhaustion guard.

Scheduling, supervision & handover

  • Workers run under launchd with KeepAlive and a restart throttle, so a dependency that is briefly down can recover instead of being hammered every few seconds.
  • The wrapper lock is taken with mkdir, but records the owner PID and only honours the lock if that PID is alive and its command line is actually that worker — so a stale lock from a crash is reclaimed rather than blocking forever. Losing a race exits busy; it never kills a live process.
  • The wrapper stays alive as a supervisor instead of exec-ing, so its exit trap can forward SIGTERM to the worker and release the lock.
  • A health subcommand probes every dependency end to end — API auth, filesystem readability, tool versions and language packs, model presence, queue ping — without taking the lock, so monitoring never disturbs the running job.
  • Handover to search: extracted text is streamed back through the internal API, chunked, and embedded, with a hard check that the returned vector dimension matches the stored width — never padded or truncated — behind both similarity and full-text indexes.

Dispatch and reconciliation are orchestrated in a visual editor, so the flow is readable by someone who is not a developer: a webhook validates on arrival, splits into the extraction and analysis branches, and merges before results are written back. The executions panel is where a retry is spotted and re-run by hand rather than by rebuilding the flow.

The console reports state, not vanity numbers: whether the queue is draining, whether stored artifacts verified, whether the model is reachable. That is the same list the health subcommand probes, surfaced for a human. A failed job is visible with its attempt count, which is what tells an operator whether to requeue it or go and look at the dependency it died on.

Design considerations

The recurring choice was to fail closed. Path safety, namespace allowlists, dependency checks and checksum verification all refuse rather than degrade — because the failure mode they prevent is a confidently wrong record in a system people will trust. Untrusted input is assumed everywhere: a document is data, never instructions.

Staying on self-hosted inference cost real operational effort — a single accelerator means one job at a time, which is exactly why priority classes and backfill sweeps exist. That trade was deliberate: keeping document content inside the network was worth more than the throughput a hosted model would have bought.

And nothing is anonymous to itself. Results carry their model, prompt version and timings; jobs carry an append-only event log. When someone asks why a record says what it says months later, there is an answer that does not involve guessing.

Engineering approach

How I work on automation projects

Six principles that shape every engagement, whatever the stack.

  1. 1

    Understand before automating

    I map the real process — including the exceptions people handle without thinking — before writing code. The stable majority gets automated; the rest gets a clean, documented path rather than a brittle rule.

  2. 2

    Design for failure

    Retries with backoff, idempotency, dead-letter queues, and meaningful error messages. Every job must fail loudly and recover safely, because at some point it will.

  3. 3

    Observability by default

    Structured logs, run history, and alerting on what actually matters. If a system's behaviour cannot be answered in a minute, the work is not finished.

  4. 4

    Keep humans in the loop

    Consequential actions get an approval gate; AI outputs get confidence thresholds and a review queue. Automation proposes and prepares — people decide.

  5. 5

    Least privilege, minimum data

    Access scopes are kept as small as the task allows, secrets stay out of code, and only the data genuinely needed is moved or retained — with limits documented.

  6. 6

    Documentation is a deliverable

    Architecture diagrams, decision records, and runbooks ship with the system. Your team should be able to operate and extend it without me.
